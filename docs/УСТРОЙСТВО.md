# Как это устроено

## Кто с кем разговаривает

```
телефон ──https:9996──> ptt.py ──┬── /m          сама страница (файл mobile.html)
                                 ├── /ctl/...  -> ctl.py   :9999  движение, позы, рация, сирена, громкость
                                 ├── /mtx2/... -> mediamtx-tiny :8890  лёгкие копии камер
                                 └── всё прочее -> dash.py :9995  кабинет (телефон его не трогает)

ноутбук ──http:9995──> dash.py           кабинет как был
          ──http:8889──> mediamtx        полные потоки cam и cam_low
```

Порты лёгкого раздатчика: API `127.0.0.1:9994`, приём RTMP `:1936`,
WebRTC `:8890`, ICE UDP `:8190`. Основной раздатчик не тронут вовсе.

## Три решения, которые стоит понять до правок

**1. Страницу телефона отдаёт `ptt.py`, а не кабинет.**
Сначала маршрут `/m` добавили в `dash.py` — и это оказалось неверно. Кабинет
строит окна камер по списку путей раздатчика, поэтому лёгкие копии тут же
превратились в четыре окна вместо двух: добавка для телефона молча переделала
чужой рабочий инструмент. Теперь `dash.py` не знает про телефон вообще, а его
файл побайтово совпадает с исходным.

**2. Лёгкие копии — в отдельном раздатчике.**
По той же причине. Плюс так проще с правами: конфиг заказчика (`mediamtx.yml`)
не редактируется, свой (`mediamtx-tiny.yml`) можно менять свободно.

**3. Исходные потоки не перекодируются.**
`camera-tiny.sh` забирает готовый поток из основного раздатчика по RTSP,
раскодирует, уменьшает и жмёт заново — аппаратно. Исходные `cam` и `cam_low`
при этом не меняются: их смотрит заказчик, и подмена содержимого оборвала бы
ему картинку.

## Ручки службы управления, которые использует страница

| ручка | что делает |
|---|---|
| `GET /state` | поза, высота, разрешение хода, пределы скорости, сирена, громкость |
| `GET /move?vx=&vy=&vyaw=&arm=1` | шаг; страница шлёт 10 раз в секунду, пока палец на джойстике |
| `GET /arm`, `/disarm`, `/stop` | разрешение хода и стоп |
| `GET /cmd/<поза>` | up, liedown, sit, risesit, hello, stretch, damp |
| `GET /siren`, `/siren/start?name=`, `/siren/stop` | список звуков и управление сиреной |
| `GET /vol`, `/vol/set?siren=&radio=` | громкость в процентах, 0–200 |
| `POST /speak/chunk?sid=&seq=&last=1` | кусок рации: сырой PCM S16LE, 16 кГц, моно |
| `POST /speak` | старый способ: вся фраза одним WAV (запасной путь) |
| `GET /ptt/on`, `/ptt/off` | заглушить слух ассистента на время рации |
| `GET /esp/<ключ>` | свет через ESP32: headlight_low_on/off, headlight_high_on/off, strobe_on/off, strobe_mode, alarm |
| `GET /sos` | тревога: мигание света ESP32 и сирена один раз |

## Рация потоком

Куски по 0.25 с уходят параллельными запросами и могут обогнать друг друга,
поэтому сервер складывает их по номеру и играет строго по порядку, в один
долгоживущий `aplay`. Потерянный кусок ждём 0.5 с и перешагиваем: дыра в
полслова лучше, чем рация, вставшая колом до конца фразы. Громкость
подстраивается на ходу по речевым кадрам — тишину и шум между словами не
усиливаем, иначе в паузах шипит.

Слух ассистента возвращает сам сервер, когда доиграет. Страница не шлёт
`/ptt/off` после последнего куска: он снял бы глушение посреди фразы, и робот
начал бы отвечать на голос из собственной колонки.

## Почему страница не делает «умного»

Все предохранители живут на роботе, а не в браузере: предел скорости, сторож
мёртвой руки (0.35 с без команд — стоп), запрет хода до явного разрешения.
Телефон может потерять связь, уснуть, закрыться — робот обязан встать сам.
Страница только перестаёт слать команды и честно показывает состояние.
